# 白名单与排除规则统一改为「名称包含即命中」

Type: grilling
Status: resolved

## 问题

审计文件树可选性规则时发现，Rust 侧用 `glob::Pattern` 做匹配（支持 `*`、`?`、`[ab]`、`[!ab]`，`*` 还能跨目录分隔符），前端 `isFileAllowed` 只把 `*` 转成 `.*`、其余元字符按字面量处理。两套语义不一致：同一条规则在树分页（Rust）与保存设置后的选择裁剪（前端）里可能给出不同结论，导致已选中的文件在界面上仍显示为选中、复制时却被后端静默丢弃。

同时 [issue 21](21-default-extension-list.md) 决定的长清单在通配符语义下才成立，而 [issue 29](29-file-exclusion-rules.md) 只承认 `*`，实际实现比票据更宽。

用户据此决定：不要通配符，规则语义要简单到「白名单放常见文本文件，排除规则去掉没用的文本文件，仅此而已」。

## 答案

- 白名单与排除规则统一为：**文件名包含规则文本即命中**，大小写不敏感。不支持 `*`、`?`、`[]` 等任何通配或正则元字符。
- `*` 在规则里没有特殊含义，解析时直接丢弃，因此早期以 `*.lock` 形式保存的规则等价于 `.lock`，旧配置无需迁移。
- 规则文本先 `trim`，再去掉尾部 `/`、去掉 `*`、再 `trim`、转小写；结果为空串时永不命中（避免空规则匹配一切）。
- 排除规则末尾带 `/` 表示只作用于文件夹，不带 `/` 表示只作用于文件。文件夹命中后其全部后代一并排除，这部分沿用 issue 29。
- 忽略目录仍是**目录名全等**匹配（trim + 大小写不敏感），不改为包含语义，避免 `build` 误伤 `build_scripts`。
- 判定顺序：先排除规则否决，再看白名单。因为没有反向规则，这与文档里「白名单后应用排除」的结果等价。
- 实时搜索把忽略目录以 `name/`、目录排除规则以 `*text*/` 交给 `fd --exclude` 剪枝，文件排除规则由应用侧 `accept_match` 复核。~~`fd --exclude` 不区分文件与文件夹，包成 `*text*` 会连带剪掉同名文件，所以排除规则一律不下推。~~ 该判断已被 [issue 52](52-fd-gitignore-and-dev-command.md) 的实测推翻：**带尾斜杠**的 glob 只匹配目录路径，`*text*/` 不会误伤同名文件，因此目录规则可以安全下推。
- 默认白名单收敛为 13 条常见文本文件规则，默认排除规则收敛为 6 条，见 [issue 21](21-default-extension-list.md) 与 `src/data/defaultSettings.ts`。
- 移除 `glob` 依赖。Rust 与前端各自实现同一套纯文本判定，由单元测试锁住行为。

## 影响

- 包含语义会让短规则覆盖面变宽：`.h` 会命中 `.html`/`.sh`/`.php`，`.c` 会命中 `.css`/`.cpp`/`.cs`/`.csv`。默认白名单据此挑选，用户自定义短规则时需自行留意。
- `.ts` 现在也会命中 `tsconfig.tsbuildinfo`，因此默认排除规则新增 `.tsbuildinfo`。
- `.lock` 一条即覆盖 `package-lock.json`/`pnpm-lock.yaml`/`yarn.lock`/`Cargo.lock`，原来的三条显式锁文件名成为冗余，已删除。

## Comments

- 用户明确要求：「不管是白名单还是排除规则，应该涉及的简单一点，不要搞得太复杂……别搞什么 `*` 复杂的匹配了，只要文件名中包含指定的字符认为规则匹配成功。」
- 本票据取代 issue 29 的通配符语义与 fd 分工、issue 21 的长清单，以及 `PROJECT_REQUIREMENTS.md` 4.2 与 `spec.md` 中的通配符口径；树中呈现、后代行为、历史恢复一致性与设置编辑方式不变。
- 同时修掉审计发现的三态勾选不对称：`getNodeTriState` 原来只挡 `isIgnored`，现在 `isExcluded` 也返回 `unchecked`。
- 验证：`cargo test --lib` 15 项通过（新增 8 项覆盖包含命中、大小写、目录规则、空规则、`*` 丢弃、忽略目录全等）；`cargo check` 与 `bun run build` 通过。桌面端人工验收待用户执行。
